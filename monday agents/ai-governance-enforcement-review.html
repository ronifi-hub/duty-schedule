Soft enforcement
S1. What does "soft" mean for an agent? SOFT
Soft enforcement today: "existing workflows keep running, can't create new ones." But agents aren't workflows a user clicks — they're autonomous background workers.

Questions:

  • Does "existing work continues" mean the agent finishes its current running task and then pauses? Or does it mean the agent stays deployed with active triggers but each trigger invocation is capped?
  • What is the agent's visible status after soft enforcement? (e.g., "Paused," "Limited," "Active with warnings")
  • Is the agent's state recoverable without any user action (auto-resume), or does someone need to do something?
S2. What counts as "new" vs "existing" work? SOFT
This is the core definitional problem for soft enforcement on agents. The answer determines whether soft enforcement gently slows the agent or effectively kills it.

Questions:

  • A running task (multi-step, currently executing) — "existing." Clear. But what about:
  • A deployed agent that is idle, waiting for a trigger — is the next trigger invocation "new"?
  • A scheduled agent (runs daily at 9am) — is tomorrow's 9am run "new"?
  • A reactive trigger (fires on board status change) — is the next status change "new"?
  • If all future invocations are "new," soft enforcement is identical to hard for agents. Is that the intent?

Risk: if not defined, engineers will guess. Different agents will handle "new vs existing" inconsistently.

S3. Scheduled agents — silent skipped runs SOFT
Scheduled agents (daily report, weekly sync) are the most likely to silently fail under soft enforcement. The agent just doesn't run. Nobody is watching.

Questions:

  • When a scheduled run is skipped, is it logged? Where? (agent activity log, admin digest, notification)
  • Does the system retry the missed run when credits are back, or is it lost?
  • Is there a visible counter of missed runs? (e.g., "missed 3 runs this week")
  • Does the enforcement backend distinguish scheduled vs event-driven agents? Does it need to?

Risk: daily report agent silently stops for a week. Nobody notices until someone asks "where's the report?"

S4. Auto-resume when credits come back SOFT
Under soft enforcement, the agent paused gracefully. When credits are available again (admin adds credits, new billing cycle), should it just pick up?

Questions:

  • Does the enforcement backend support auto-resume (agent restarts on its own when credits refill)?
  • If 10 agents are paused and credits refill, do they all resume at once? Is there a stampede/burst risk?
  • Does the agent resume from where it left off (next scheduled run, next trigger) or does it start fresh?
  • Is there a notification when an agent auto-resumes? ("Agent [name] resumed — credits available")
Hard enforcement
H1. What does "hard" mean for an agent? HARD
Hard enforcement = stricter block. But for an autonomous agent, "stop immediately" has real consequences — unlike clicking a button in Sidekick where you just can't click again.

Questions:

  • Does "hard" mean the agent is interrupted mid-action (immediate kill) or finishes the current atomic action then stops (graceful hard stop)?
  • What is the agent's visible status? (e.g., "Stopped," "Blocked")
  • Can the agent be hard-stopped by the enforcement backend automatically (limit hit), or only by admin action (admin manually hard-blocks)?
  • Is hard enforcement per the admin's choice (admin picks soft vs hard per agent) or system-decided (e.g., soft at 100%, hard at 120%)?
H2. Mid-task interruption and partial work HARD
The defining risk of hard enforcement. An agent mid-way through a multi-step task is stopped. Data may be half-written.

Questions:

  • Does the enforcement check happen before each action (pre-check: clean break before next step) or after credits are consumed (post-check: could overshoot)?
  • For multi-step tasks: is there a concept of a "transaction" (all-or-nothing) or is partial completion the expected outcome?
  • If partial: is there a log of where the agent stopped? (e.g., "processed 47 of 100 rows")
  • Who is responsible for cleaning up partial work — the user manually, the agent on restart, or the system?
  • Can the agent overshoot the limit to finish a critical atomic action (e.g., complete sending an email), or is it a hard cut regardless?

Risk: 47 of 100 rows updated. Email sent but no follow-up. Customer-facing data left in a broken state with no indicator of where the agent stopped.

H3. Manual restart after hard stop HARD
After a hard stop, the agent should NOT auto-resume — someone needs to consciously restart it. But what does that look like?

Questions:

  • When credits are added after a hard stop, does the agent stay stopped until an admin manually restarts?
  • Does the admin see a "Restart agent" CTA on the agent card, or do they need to go to settings?
  • On restart, does the agent retry the interrupted task, or does it start fresh from the next trigger?
  • If the agent was mid-task: is there a "Review incomplete work" step before restart?
  • Can a member request restart, or is it admin-only?

Risk: admin adds credits but forgets to restart. Agent stays dead indefinitely. Nobody notices.

H4. Immediate notifications for hard stops HARD
Hard stops are urgent — they can leave broken work. A daily digest is not enough. The admin needs to know now.

Questions:

  • Does the enforcement backend support real-time push notifications for hard stops (not just digest)?
  • What channels? (in-app notification, email, webhook, Slack integration)
  • Does the notification include context about what was interrupted? (e.g., "stopped mid-task: updating board [name], 47 of 100 rows processed")
  • If the agent was doing customer-facing work (emails, support tickets), is there an escalation path beyond notification?
General (applies to both soft and hard)
G1. Enforcement level: per-user or per-agent? GENERAL
Today the Admin Panel sets per-user limits. But one user can have multiple agents with very different criticality.

Questions:

  • Does the enforcement backend support per-agent limits, or only per-user?
  • If per-user only: is per-agent on the roadmap? When?
  • If a user has 5 agents and hits their user-level limit, which agent stops first? Random, FIFO, or admin-prioritized?
  • Can we have both — per-agent limit (primary) and per-user ceiling (secondary cap)?

Risk if per-user only: one runaway agent kills all other agents for that user. No way to protect critical agents.

G2. Account-level vs agent-level exhaustion GENERAL
Two different things: a single agent hits its own limit, vs the entire account runs out of credits. Both can happen, and the messaging/CTA is different.

Questions:

  • Are these two separate enforcement checks (agent limit + account limit) or one?
  • Which takes precedence? Can an agent have credits left but be blocked because the account pool is empty?
  • If an admin buys more account credits, do agent-level limits also increase, or are they independent?
G3. Blast radius: shared credit pools GENERAL
Shared pools (per-user or per-account) mean one heavy agent can exhaust credits for everyone.

Questions:

  • Does the backend support isolated pools (per-agent) or only shared?
  • If shared: is there priority/ordering when the pool runs out?
  • Can an admin set a "reserved" allocation for critical agents within a shared pool?
  • When multiple agents are affected, does the notification list all of them or just the one that triggered?

Risk: User B's critical agent dies because User A's experimental agent burned through the shared pool.

G4. Agent chains and cascading failure GENERAL
Agent A triggers Agent B. If A is blocked, B never fires — but B looks healthy because it has credits.

Questions:

  • Does the backend know about agent dependencies? Can it flag downstream impact?
  • When Agent A is blocked, should Agent B show "waiting — depends on Agent A"?
  • Should chained agents share a credit pool, or stay independent?
  • Is there visibility for the admin to see "A triggers B" anywhere today?

Risk: cascading silent failure. Admin thinks Agent B is fine. It's actually dead because its trigger (Agent A) is blocked.

G5. Orphaned agents (owner left the company) GENERAL
User created an agent, then left the org. Agent is still running, consuming credits. It hits a limit.

Questions:

  • Does the backend attribute credits to the creator or to the account?
  • When a user is removed, what happens to their agents? Paused? Transferred? Keep running under account pool?
  • Who gets the limit notification — all admins? Nobody?
  • Is there a concept of agent ownership transfer?

Risk: agent silently dies. Nobody is notified. Nobody knows it exists.

G6. Member → Admin request flow GENERAL
Members can't buy credits or change limits. They need a "Request more credits" CTA that notifies the admin.

Questions:

  • Does a "request credits" mechanism already exist, or does product need to build it?
  • What context should the request include? (agent name, usage, member name, link to agent settings)
  • Who receives it — agent owner, all admins, or billing admin?
  • Is there a rate limit on requests? (one per agent per day)
  • When the admin acts, does the member get a confirmation? ("Agent is back online")
G7. Notification channels and thresholds GENERAL
Agents run in the background. Without the right notification at the right time, enforcement happens silently.

Questions:

  • What channels does the backend support? (in-app, email, webhook, daily digest)
  • Can notifications be per-agent (to agent owner) or only per-account (all admins)?
  • Is there a warning threshold before limit (e.g., 80%)? Is it configurable?
  • Does the backend send notifications, or does product subscribe to events and build them?

Going into the meeting

The enforcement team owns the backend; we own the in-product experience. Walk out with answers to:

  1. What exists today — which topics are already decided/built?
  2. What's on their roadmap — per-agent limits, hard enforcement, notification hooks, warning thresholds.
  3. Where we need to influence — if the backend doesn't support what we need, make the case now before it's built.
  4. API contract — what events/APIs does the enforcement backend expose so we can build messaging, CTAs, and notifications?
